FPGA Studio — Native macOS HDL IDE

A native Mac app I wrote so I could edit VHDL and Verilog, simulate, build a bitstream, and program a Cyclone V board without leaving the editor — and without installing Quartus.

The App

Screen recording of FPGA Studio running the blinky project: edit, simulate, inspect the waveform, build a Cyclone V bitstream, and program SRAM on the C5G.

Project Overview

  • Role: solo project, ongoing
  • What it is: a native Apple-silicon macOS IDE (Swift 6 / SwiftUI) for portable VHDL, Verilog, and SystemVerilog projects
  • Target board: Terasic Cyclone V GX Starter Kit (C5G), device 5CGXFC5C6F27C7
  • Flow: Check project → Simulate → Build bitstream → Detect board → Program SRAM
  • On hardware: a blinky bitstream programmed over JTAG into SRAM; green LEDG toggles from an on-chip counter
  • Not claimed: a finished processor, persistent flash programming, or Quartus-equivalent coverage of Cyclone V hard blocks

Why Build It

I wanted a real FPGA flow on the machine I already work on. Quartus and ModelSim are what the courseware expects; on an Apple-silicon Mac they are a VM and a pile of installers. I also wanted to understand the open-source path end to end — not just click Build in someone else’s GUI, but own the editor, the project format, the subprocess boundary, and the programmer.

So I wrote the IDE myself. The backends are not mine: Yosys, GHDL, nextpnr-mistral / Mistral, Icarus Verilog, Verilator, and openFPGALoader. What I built is the native shell around them — project files that are ordinary folders, a TextKit editor, simulation and waveform, pin/QSF checks, a bundled toolchain, and a SRAM-first programmer aimed at one board I actually own.

The Flow

A project is a folder with fpga-project.json, HDL sources, a QSF constraints file, and optional testbenches. Build products land under .fpga/build. Nothing about that format is locked to the app; you can open the same folder in a text editor.

What the App Does

  • Editor. TextKit source view with line numbers, syntax coloring, search, bracket matching, autosave, and clickable diagnostics from the tools.
  • Simulation. Verilog/SystemVerilog through Icarus, VHDL through GHDL, lint through Verilator, and a native VCD waveform viewer. Mixed-language simulation is not in this version.
  • Constraints. C5G pin assignments are searchable. The checker flags duplicate pins, unknown pins, missing ports, I/O-standard mismatches, and direction errors before you spend a build on them.
  • Build. Yosys (with the GHDL plugin for VHDL) then nextpnr-mistral. Cyclone V support upstream is experimental; inferred memory and multiply map to logic in the default path. M10K, DSP blocks, LPDDR2, transceivers, and PCIe are outside what I treat as working.
  • Programmer. Detect the USB-Blaster, write SRAM, done. SRAM is temporary on purpose. Persistent EPCQ flash stays behind a lock until that path is validated on this board. I have not used flash from this app.
  • Toolchain. The release app ships Yosys, GHDL, nextpnr-mistral, Icarus, Verilator, and openFPGALoader inside the bundle. First launch unpacks them into Application Support. No Homebrew required to run a project.

On the Board

The first design that went onto the C5G through this flow is blinky: a counter on CLOCK_50_B5B driving LEDG[0] (PIN_L7). After Program SRAM, the green LED above the push-buttons toggles. That is the check that the editor, the bitstream, the pin file, and the programmer agree with the hardware.

Two board details matter more than they look. The RUN/PROG slide switch (SW11) has to be in RUN for JTAG SRAM programming. And the tiny LED next to the USB-Blaster is activity for the programmer, not user I/O — the output you actually watch is LEDG.

How It’s Built

The UI is SwiftUI. The editor is AppKit/TextKit. The pipeline is a Swift package that shells out with argument arrays only — no interpolated shell strings — then streams logs and supports cancel. Environments are sanitized. One project gets one build-directory lock so two Builds cannot clobber each other.

Tests cover the project manifest, path safety, QSF validation, VCD parsing, templates, and that the subprocess layer does not take a shell. Simulation and synthesis are exercised in CI-style runs on arm64 macOS. The physical board work is mine, on the desk, through SRAM.

Current Status & What’s Next

The app is usable for the C5G SRAM loop I described. Blinky is on the board. I still treat Cyclone V place-and-route as experimental, keep flash locked, and am not calling this a replacement for Quartus. Apple’s Gatekeeper still wants a right-click Open because the build is ad-hoc signed, not notarized.

Next is tightening the C5G labs that ship with the app, then notarized distribution if the SRAM path stays boring. More devices only after this one stays boring.
