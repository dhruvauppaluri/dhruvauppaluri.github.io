FPGA Studio — Native macOS HDL IDE

A native Apple-silicon Mac app that takes an HDL project from source and simulation to a Cyclone V bitstream and safe hardware programming—without a Quartus VM or a separately installed toolchain.

Download v2026.09.1 View source

The App

This recording shows the real v1 app running its complete first-project path: edit the C5G Blinky design, check it, simulate it, inspect the generated waveform, build an RBF bitstream, detect the board, and program volatile SRAM.

Project Overview

  • Status: independent project, actively developed; v2026.09.1 is available as a DMG pre-release
  • Platform: Apple silicon (M1 or later) on macOS 15 Sequoia or newer
  • Languages: VHDL, Verilog, and SystemVerilog in portable folder-based projects
  • Target board: Terasic Cyclone V GX Starter Kit (C5G), device 5CGXFC5C6F27C7
  • Flow: Check project → Simulate → Build bitstream → Detect board → Program SRAM
  • Distribution: the release bundles the synthesis, simulation, place-and-route, and programming tools; no Homebrew setup is required
  • Hardware result: the demo’s blinky bitstream is programmed over JTAG into SRAM and drives the board’s green LED
  • Deliberate limits: no mixed-language simulation, no finished RV32I processor, and no claim of Quartus-equivalent hard-block coverage

Why Build It

I wanted a real FPGA workflow on the machine I already use. The conventional course flow assumes Quartus and ModelSim; on an Apple-silicon Mac that usually means a virtual machine and a separate stack of installers. I also wanted to understand the open-source path end to end—not just click Build in an existing GUI, but design the editor, project format, tool boundary, diagnostics, and programming safeguards around it.

FPGA Studio is that native layer. It brings together Yosys, GHDL, nextpnr-mistral / Mistral, Icarus Verilog, Verilator, and openFPGALoader; those backends remain their own open-source projects. My work is the Swift application around them: the project model, TextKit editor, guided workflow, validation, waveform UI, toolchain packaging, and board-specific safety policy.

Built to Grow With the User

I wanted FPGA Studio to be an editor that someone new to FPGA development could open and actually follow. Beginner mode starts with Blinky, recommends one next action at a time, explains unfamiliar terms in plain language, and lets the user validate and simulate a design before any board is connected. The tour, progress guide, safe defaults, and Learn Center make the workflow visible instead of assuming prior toolchain knowledge.

It is not a separate “beginner version” of the app. Hobbyist and Professional profiles reveal more direct controls, raw diagnostics, build artifacts, backend status, and advanced synthesis detail over the same project format and feature set. As a user gains experience, the guidance can move out of the way without forcing them to leave the editor they learned in.

The Flow

A project is an ordinary folder with a versioned fpga-project.json manifest, HDL sources, a QSF constraints file, and optional testbenches. Deterministic build products land under .fpga/build. The format is intentionally inspectable and does not lock the source into the app.

What the App Does

  • Native workspace. A welcome window, unified toolbar, project navigator, source tabs, inspector, issues, logs, simulation, waveform, and programmer panels—all built with SwiftUI and AppKit.
  • Editor. A TextKit source view with line numbers, SF Mono, syntax coloring, search, bracket matching, undo, autosave, and clickable diagnostics.
  • Experience profiles. Beginner, Hobbyist, and Professional modes tune guidance and technical detail without gating capabilities.
  • Templates. Blank HDL, C5G Blinky, and an RV32I Lab scaffold. The processor lab supplies interfaces, a board wrapper, ROM image, and directed tests; it intentionally does not contain a finished CPU.
  • Simulation. Verilog/SystemVerilog through Icarus, VHDL through GHDL, lint through Verilator, and a native VCD waveform viewer. Mixed-language simulation is not in this version.
  • Constraints. C5G pin assignments are searchable. The checker flags duplicate pins, unknown pins, missing ports, I/O-standard mismatches, and direction errors before you spend a build on them.
  • Build. Yosys (with the GHDL plugin for VHDL) then nextpnr-mistral. Cyclone V support upstream is experimental; inferred memory and multiply map to logic in the default path. M10K, DSP blocks, LPDDR2, transceivers, and PCIe are outside what I treat as working.
  • Programmer. Board detection and volatile SRAM programming are the default hardware path. A guarded EPCQ flash flow also exists behind advanced controls, explicit artifact confirmation, and post-write detection, but I do not yet claim that path as hardware-accepted.
  • Managed toolchain. The release app carries every backend in a signed bootstrap archive, verifies it, and atomically installs it into Application Support on first launch. Installed toolchain versions can be activated again for rollback.

The Hardware Proof

The first design taken through the complete flow is Blinky: a counter clocked by CLOCK_50_B5B drives LEDG[0] on PIN_L7. After programming SRAM, the green LED above the push-buttons toggles. That small result checks the whole vertical slice—the editor state, source and pin validation, simulation, RBF generation, USB-Blaster connection, and physical I/O assignment.

Two board details matter more than they look. The RUN/PROG slide switch (SW11) has to be in RUN for JTAG SRAM programming. The tiny LED next to the USB-Blaster shows programmer activity; the design output to watch is LEDG.

Engineering the Boundary

The UI is SwiftUI, while the source editor is an AppKit/TextKit component. The build pipeline lives in a separate Swift package and launches tools with argument arrays rather than interpolated shell commands. It sanitizes child-process environments, streams logs, supports cancellation, and applies a per-project build-directory lock so concurrent builds cannot clobber each other.

Hardware writes are treated as a separate safety boundary. Before programming, the app checks the board profile, JTAG identity, artifact device, build fingerprint, timestamp, size, and digest. Persistent flash adds an explicit acknowledgement plus sleep and app-termination protection during the non-cancellable write.

Tests cover manifest round trips, safe paths, QSF and port validation, diagnostics, VCD parsing, template integrity, shell-injection resistance, real Icarus simulation, and RV32I scaffold compilation. Release packaging also smoke-tests the bundled tools in an isolated prefix without Homebrew on the path.

Current Status & Limits

The v2026.09.1 pre-release is usable for the C5G SRAM loop shown above, and the software build, simulation, and packaging paths are tested on arm64 macOS. Cyclone V place-and-route remains experimental upstream. Advanced hard blocks—including M10K memory, DSPs, LPDDR2, transceivers, PCIe, and advanced PLLs—are outside the validated default path.

The guarded persistent-flash path is implemented but still awaiting hardware acceptance, and the RV32I template is a lab scaffold rather than a completed processor. I am not presenting FPGA Studio as a drop-in replacement for Quartus. The current DMG is ad-hoc signed, so Gatekeeper requires a one-time right-click Open; notarized distribution is still ahead.

Next I am tightening the C5G labs, completing flash acceptance on the target board, and hardening distribution. Support for more devices comes after the first board’s workflow is repeatable.
