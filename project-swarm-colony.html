Apollo Colony — Swarm Robotics Platform (In Progress)

A multi-robot swarm platform, starting with one robot: Apollo1, the "queen," built on the chassis from my Apollo 1 rover. It now drives itself around obstacles using a camera and a time-of-flight sensor together, and I recently got a touchscreen panel talking to it over WiFi so I can start/stop it and watch its status without a laptop in the loop.

github.com/dhruvauppaluri/swarm-project

Project Overview

  • Role: solo project, ongoing
  • Status: drive, distance sensing, and camera-based obstacle avoidance (fused with the ToF sensor) are all verified live on the first robot; a touchscreen control panel is flashed and verified live end-to-end; a MuJoCo sim-to-real RL pipeline is physically stable but doesn't have a working obstacle-avoidance policy yet; swarm/multi-robot logic hasn't started
  • Key hardware: the chassis from the Apollo 1 rover build, rebuilt around 2-motor differential drive — ESP32-WROOM-32 DevKitC, a single L298N H-bridge, a fixed-mount VL53L0X time-of-flight sensor, a Seeed XIAO ESP32S3 Sense camera board, and a SeeedStudio SenseCAP Indicator D1 (ESP32-S3 + RP2040, 480×480 touchscreen) as a control panel
  • Stack: Arduino/C++ firmware, Python (FastAPI, WebSocket, OpenCV, YOLOv8n via ultralytics, pyserial), LVGL for the touchscreen UI, macOS blueutil for Bluetooth session management, MuJoCo + Gymnasium + Stable-Baselines3 (PPO) for the sim-to-real training pipeline
  • Repository: github.com/dhruvauppaluri/swarm-project

Note: this builds on Apollo 1, the WeaveHacks 4 EEG rover — I'm reusing that chassis, but everything on top of it is a fresh rebuild in its own swarm-project repo. The Arduino Uno and per-motor transistors are gone; it's an ESP32 platform now, with a new drive layout, a WebSocket/Bluetooth bridge, a camera-based perception stack, and a touchscreen panel. I also happened to name this robot "Apollo1" too, so I want to flag that up front — same name, different robot, no relation beyond the recycled frame.

Objective

The eventual goal is a colony of small robots coordinating as a swarm. That's a long way off, and I don't think it's worth chasing until one robot can reliably drive, sense, avoid obstacles, and stay reachable on its own. So that's what Apollo1 has been: the old chassis, rebuilt with a simpler drive layout, real perception, and enough control surfaces — a web D-pad, now a touchscreen panel — to actually trust it before I start on a second robot.

It's paid off. This isn't a hardware bring-up exercise anymore; it's a robot that drives itself around obstacles with a camera, and I can start, stop, and watch it from a touchscreen over WiFi. Getting multiple robots talking to each other is still the next big step, and I haven't started on it yet.

System architecture

  • Chassis: the platform from the Apollo 1 rover build, rebuilt around a single L298N H-bridge driving 2 motors in differential drive — simpler and more reliable than the 4-motor/2-module skid-steer layout it replaced, after a persistent single-channel wiring fault on the old layout.
  • Drive: latched commands (w/a/s/d/x) over both USB serial and Bluetooth SPP, mirrored to both at once so either link can debug the other.
  • Distance sensing: a fixed-forward VL53L0X time-of-flight sensor, plus a firmware-side autonomous obstacle-avoidance state machine.
  • Camera-based obstacle avoidance: a Seeed XIAO ESP32S3 Sense streams MJPEG over its own WiFi link; a Python script runs YOLOv8n on the live feed, decides a drive command from detected-object position and size, and fuses it with the VL53L0X reading — the point sensor can only escalate caution, never override the camera toward "clear." Verified live: a held obstacle triggered an immediate stop at the frame it crossed a distance threshold, with auto-resume once it was pulled back.
  • Control bridge: a FastAPI + WebSocket server (control/web_ui/server.py) owns the single Bluetooth serial connection to the robot and fans it out to any number of clients at once — the browser D-pad, the vision script, and the touchscreen panel all share the same link without fighting over the serial port.
  • Touchscreen control panel: a SeeedStudio SenseCAP Indicator D1 (ESP32-S3 + RP2040 co-processor, 480×480 touchscreen) runs an LVGL UI with a tabbed layout — a live "Apollo 1" start/stop + status tab, and a reserved "Drone 1" placeholder tab for the next robot. Since the Indicator's ESP32-S3 only has BLE radio hardware (no Classic Bluetooth), it reaches the robot over WiFi as a WebSocket client of the same bridge server the browser D-pad uses.
  • Sim-to-real RL (in progress): a MuJoCo model built to the robot's real measured dimensions, wrapped as a Gymnasium environment with the same discrete drive commands and the same 6 sensor readings (VL53L0X + a rangefinder fan standing in for the camera's field of view) the real robot actually has, trained with PPO via Stable-Baselines3. The idea is to train obstacle-avoidance robustness in simulation before ever risking it on the real hardware.

Implementation

Chassis redesign: from 4-motor skid-steer to 2-motor differential drive

Apollo1 started on the same 4WD chassis as Apollo 1, driven by two L298N modules in skid-steer. One motor channel just wouldn't spin, and a swap test made it obvious this wasn't the motor or the driver — a known-good motor failed on that same channel, and the "bad" motor was fine everywhere else, so it had to be a wiring fault I didn't want to chase down further. I dropped the front two wheels for a free-swiveling caster and rebuilt the drive around a single L298N and two rear motors instead. Simpler electronics, one less thing to go wrong — and once the camera gave the robot wide-field awareness with no moving parts, the servo that used to pan the distance sensor didn't have a job anymore, so I retired it for good.

Camera-based obstacle avoidance

control/vision/object_avoidance.py runs YOLOv8n on the XIAO ESP32S3 Sense's live MJPEG stream. It turns where an object sits in frame and how big it looks into a drive command, then cross-checks that against the VL53L0X reading over serial — the point sensor can escalate caution but can't override the camera toward "all clear." A point-blank reading stops the robot immediately, no debounce; a moderately close one triggers a turn even if the camera thinks it's fine. I've tested both live against a real obstacle, hand-held in front of the robot while it drove — it stopped right on cue and resumed automatically once I pulled the obstacle back.

SenseCAP Indicator touchscreen panel

This one took a while to get right. The touchscreen sketch (firmware/sensecap_display_control) draws an LVGL tab view with START/STOP buttons and a status label that just mirrors whatever the robot's own firmware last printed — forwarded through the WebSocket bridge as plain text. Before I flashed anything, I checked what was actually already running on the board, and it turned out to still be someone else's old hackathon demo: an air-quality logger on the RP2040 side, and a WiFi app on the ESP32-S3 that I could see live over serial and, read-only, straight out of the flash image. Once I got to actually flashing my own sketch, the upload kept failing at the default baud rate (921600 corrupted mid-transfer on this board's USB path) — dropping to 115200 fixed it. Getting from "screen renders" to "screen actually shows live data" took one more real bug, in the bridge server itself (see below).

Display and touch bring-up (the ST7701 panel init, the PCA9555 IO-expander wiring, the software-SPI bus, the LVGL↔Arduino_GFX glue) isn't mine — it's adapted near-verbatim from LongDirtyAnimAlf/SenseCap, which is the reference implementation Seeed's own wiki points to for this board. The touch driver is mmMicky/TouchLib, also linked from Seeed's docs. What's mine is the WiFi/WebSocket client, the start/stop/status UI, and the tabbed layout for multiple robots.

Web control UI & bridge

control/web_ui/server.py owns the one Bluetooth serial connection to the robot and fans it out to whoever's connected over WebSocket — the browser D-pad, the vision script, the touchscreen panel — so they're not fighting each other for the port. The browser page (control/web_ui/index.html) is a plain D-pad with keyboard shortcuts and a running log of what got sent and what came back.

Sim-to-real RL: MuJoCo + PPO (in progress, not yet a working policy)

The plan is to train obstacle-avoidance robustness in simulation before ever putting a half-trained policy on real hardware. control/sim/ generates a MuJoCo model from the robot's actual measured dimensions (wheelbase, wheel size, chassis footprint, VL53L0X mount height), wraps it as a Gymnasium environment, and trains against it with PPO via Stable-Baselines3. The action space is the same five discrete commands the firmware accepts, not raw wheel velocities, and the observation is the same 6 sensor readings the real robot has — a rangefinder standing in for the VL53L0X, plus a fan of five more approximating the camera's field of view — specifically so a trained policy isn't leaning on information the real robot doesn't have.

Right now it's stable but not useful yet. The first full training run looked great on paper — reward climbing, episodes surviving to the step cap — until I actually watched the policy drive and realized it had learned to shuffle forward and backward in place near its spawn point, which happens to be far enough from any obstacle to never crash. The reward was paying for raw distance traveled, so wiggling scored the same as real progress. I fixed that (reward now only counts progress in the direction the robot's actually facing), retrained, and got a policy that at least moves — except it just drives dead straight until it hits something, because the only obstacle-avoidance signal was a penalty on actual collision, which turned out to be too weak and too late for the algorithm to learn "turn before you get there." That part's still unsolved as of this writing.

Debugging & iteration

SenseCAP display: the bridge kept dropping the connection right after handshake

Once the panel was flashed, I couldn't tell if it was working from serial — turns out Serial output just doesn't route over this board's USB path at runtime, so the only real signal was the screen itself, which was at least rendering. But it connected to the bridge and dropped again immediately, over and over, three times in under ten seconds. The server-side traceback gave it away: the bridge sent its first status message to a client before it had even entered its own try/except block, so when the ESP32's WebSocket library closed the connection right after the handshake — apparently it needs a beat before it's ready to receive anything — the exception went uncaught and the dead client just sat there. I moved that first send inside the try and added a short delay before it, and that was it: the connection held for 25+ seconds straight afterward instead of dying every few. I knew it actually worked once the display's status label started showing real live data from the bridge instead of a placeholder string.

Bluetooth SPP — three stacked bugs, then a fourth I'm still living with

Getting Bluetooth SPP to reconnect cleanly took three separate fixes, and I only found any of them by reading raw system logs instead of guessing from what I was seeing on screen: macOS caching a stale RFCOMM channel after a reboot (fixed by forcing a fresh unpair → pair → connect before every session), the ESP32's own bond store disagreeing with a freshly re-paired host key (fixed by clearing the firmware's bond on every disconnect, not just at boot), and a macOS race where pairing would finish before the device's name resolved, which silently killed the serial port even though the Bluetooth link itself was fine (fixed with a short discovery scan in between). There's a fourth failure mode I haven't fully solved: sometimes the link just goes quiet — reports connected, accepts writes, and nothing ever comes back. It's not any of the earlier three; those all fail loudly somewhere specific. For now the fix is just restarting the bridge server, which forces a clean reconnect. I'd like a real auto-recovery path instead of a manual restart, but haven't built it yet.

VL53L0X — "no I2C devices found" traced to unsoldered header pins

  • Symptom: a fresh VL53L0X breakout scanned as completely empty on the I2C bus, across a long list of ruled-out causes — XSHUT floating vs. tied high, VIN at 3.3V vs. 5V, SDA/SCL swapped, alternate GPIOs, a slower I2C clock, even a second brand-new sensor.
  • Cause: the header pins were never soldered — just pushed through the board's through-holes and resting against the breadboard. A multimeter continuity check passed every time, because pressing a probe onto the pin forced a contact that wasn't present in the board's resting state.
  • Confirmed by: running the I2C scan in a tight loop while physically pressing on the header pins — the sensor showed up correctly at its real address, 0x29, during sustained contact, and dropped out the instant contact broke.
  • Fix: solder the header pins. No wiring or firmware change was needed — the pin assignments and test sketch were already correct.

The lesson I keep relearning: a continuity check with a multimeter only proves a connection is good while the probe is pressed on it. It can't catch a joint that's only bad under the board's own resting weight. The WebSocket bug above was the same shape of problem in a totally different layer of the stack — everything looks fine right up until you actually watch it fail.

The sim physics only broke once I plugged in real numbers

I built the MuJoCo model with placeholder dimensions first, checked it didn't explode, then swapped in the robot's real measurements — and it immediately did explode: the chassis flung across the room at multiple meters per second, spinning at 30+ radians a second within a single 5-millisecond physics step. Two bugs, both hidden by the placeholder numbers being small enough to get lucky. First, the formula placing the caster wheel had chassis-length terms that canceled out algebraically to nothing, leaving just a sign error that put the caster behind the driven wheels instead of in front — harmless with an 8cm placeholder offset, but with the robot's real 15cm offset it left the whole front of the chassis unsupported. Second, even after fixing that, the wheel motors were applying enough instantaneous torque to spin up against the wheels' tiny rotational inertia that the reaction alone was enough to throw the chassis — fixed by capping the actuator torque to something a small motor could realistically produce, instead of letting the physics solver assume infinite torque was available to hit the target speed instantly.

Same lesson as the VL53L0X header pins, really: a check that passes under one set of conditions (small placeholder numbers, a probe pressed on a pin) doesn't mean the underlying thing is actually correct. It just means you haven't hit the case that exposes it yet.

Current status

Where things stand right now: the rebuilt 2-motor chassis drives cleanly in both directions and pivots over Bluetooth. The camera and the VL53L0X are fused and I've watched the override stop a real obstacle, twice. The SenseCAP touchscreen panel is flashed, renders correctly, and holds a live connection to the bridge with a real-time status feed. The one thing still nagging me is that the Bluetooth link between the bridge and the robot can go quiet under live use — restarting the bridge server fixes it, but I haven't built a real auto-recovery path yet. On the sim side, the physics are stable and built to the robot's real dimensions, but I don't have a trained policy that actually avoids obstacles yet — it currently just drives straight into things, and I'm mid-way through fixing the reward signal so it learns to turn before it gets there instead of after.

Next up: get the sim actually learning real avoidance behavior, fix the Bluetooth link for real instead of restarting it by hand, then start on the swarm part — multiple robots coordinating, which is the whole reason this is called a "colony." Right now it's one robot. The swarm is still ahead of me.

Repository

Everything's at github.com/dhruvauppaluri/swarm-project. Flash firmware/motor_polarity_test/motor_polarity_test.ino for drive and sensing, or firmware/sensecap_display_control for the touchscreen panel.
