Apollo Colony — Swarm Robotics Platform (In Progress)

A multi-robot swarm platform, starting with Apollo1: a skid-steer "queen" robot that reuses and upgrades the chassis and hardware from the Apollo 1 rover build, with dual-mode USB/Bluetooth control, a web D-pad, and a servo-mounted time-of-flight sensor for the perception layer.

github.com/dhruvauppaluri/swarm-project

Project Overview

  • Role: solo project, ongoing
  • Status: hardware and drive/control stack verified end-to-end on the first robot; swarm/autonomy logic not started yet
  • Key hardware: the 4WD chassis from the Apollo 1 rover build, reused and upgraded — ESP32-WROOM-32 DevKitC (replacing the Arduino Uno), 2x L298N H-bridges (replacing per-motor transistor switching), 4x TT/N20 gearmotors (skid-steer), SG90 servo, VL53L0X time-of-flight sensor
  • Stack: Arduino/C++ firmware, Python (pyserial, FastAPI, WebSocket), macOS blueutil for Bluetooth session management
  • Repository: github.com/dhruvauppaluri/swarm-project

Note: this builds on Apollo 1, the WeaveHacks 4 EEG rover — that project's 4WD chassis and hardware are the starting point here, but this is a separate, ongoing rebuild in its own swarm-project repo: Arduino Uno swapped for an ESP32, per-motor transistor switching swapped for L298N H-bridges, and a new Bluetooth SPP control stack and perception arm added on top. The robot is internally named "Apollo1" here too (the queen of the planned "Apollo Colony" swarm), which is a coincidence worth flagging so the two aren't mixed up.

Objective

The goal is a colony of small robots that can eventually coordinate as a swarm. Before any swarm logic makes sense, one robot has to actually drive, sense, and stay reachable — that's Apollo1, the queen: the existing Apollo 1 rover chassis, carried over and upgraded with new drive electronics and a control link, to shake those out before a second robot is even started.

Right now the project is a hardware and control-plane exercise: skid-steer drive verified, a dual USB/Bluetooth command path that survives reconnects, and a servo + distance sensor front arm for basic perception. The actual swarm behavior — multiple robots, obstacle avoidance, coordination — is the next phase, not yet built.

System architecture

  • Chassis: the existing 4WD platform from the Apollo 1 rover build, reused rather than redesigned — the upgrade work is in the electronics and control stack on top of it.
  • Drive: 4x TT/N20 gearmotors through 2x L298N H-bridges (left side and right side each on their own driver), skid-steer only — no independent steering axis.
  • Control link: ESP32 BluetoothSerial (classic SPP, device name "Apollo1") mirrored to USB serial — every command and status line goes out both channels at once, so USB and Bluetooth are always interchangeable for debugging.
  • Host bridge: a FastAPI + WebSocket server (control/web_ui/server.py) owns the Bluetooth serial connection and fans it out to any number of browser clients, running a scripted blueutil unpair → inquiry → pair → connect sequence on every session.
  • Web control: a WebSocket-driven D-pad (control/web_ui/index.html) with keyboard support, sending latched drive commands (w/a/s/d/x) that hold state on the ESP32 until the next command changes them.
  • Perception (in progress): SG90 servo sweeps a VL53L0X time-of-flight sensor on the front arm — verified working in an isolated test sketch, not yet merged into the drive firmware.

Implementation

Reusing and upgrading the Apollo 1 hardware

Rather than starting a new chassis from scratch, this project takes the 4WD platform built for Apollo 1 and rebuilds the electronics on top of it: the Arduino Uno and per-motor transistor switching are replaced with an ESP32-WROOM-32 and 2x L298N H-bridges, and the control link, drive firmware, and perception hardware are all new. The physical frame is the one constant between the two projects — everything driving and sensing on it is different.

Motor polarity and drive

firmware/motor_polarity_test/motor_polarity_test.ino started as a pure bring-up sketch: apply the same logical "forward" signal to every channel, left side then right side, so a mismatched or reversed motor lead shows up as one wheel spinning opposite its partner — a mechanical/electrical check with no sensors and no swarm logic involved. That same sketch now also carries the latched skid-steer drive commands the web D-pad uses: forward, backward, and pivot turns (one side forward, other side backward), all at roughly 50% duty.

Bluetooth control link

Every firmware sketch mirrors all output to both USB serial and Bluetooth SPP, so the same command set (r/l/g/f for motor tests, w/a/s/d/x for drive) works identically over either link. That symmetry made debugging tractable — USB serial could confirm what the firmware was doing while Bluetooth was misbehaving, without needing a second code path.

Web control UI

control/web_ui/server.py holds one shared Bluetooth serial connection and fans status/RX lines out to every connected WebSocket client, so the D-pad page can be opened from a phone or a laptop without fighting over the serial port. The page itself (control/web_ui/index.html) is a plain D-pad with keyboard shortcuts and a live log of sent commands and device responses.

Servo + ToF perception arm

firmware/servo_sensor_test/servo_sensor_test.ino tests the SG90 (GPIO13) and VL53L0X (I2C, SDA=21/SCL=22) independently of the drive firmware — servo sweep, single or continuous distance reads, and a raw I2C bus scan. Both are now confirmed working end-to-end, including a combined sweep-and-range test that logs distance at each servo angle.

Debugging & iteration

Bluetooth reconnects — three separate, stacked bugs

Getting Bluetooth SPP to reconnect cleanly after the first session took three independent fixes, each found by reading raw system logs instead of guessing from symptoms:

  • macOS SDP channel caching — after an ESP32 reboot, macOS was still connecting to the old cached RFCOMM channel number from the original pairing, which the rebooted device wasn't listening on anymore. /dev/cu.Apollo1 would open and write() would succeed, but nothing reached the board. Fix: blueutil --unpair → --pair → --connect before every session forces a fresh SDP query.
  • ESP32 bond/link-key mismatch — once the host started re-pairing every session, the Mac generated a new link key each time while the ESP32's own bond store still held the previous one, so the secure RFCOMM layer got silently rejected a few seconds into the handshake (HCI status 719). Fix: the firmware now clears its own bond for the host's MAC address every time a client disconnects (pollBondReset()), not just once at boot.
  • macOS name-resolution race — confirmed via log stream --predicate 'process == "bluetoothd"': right after unpairing, macOS hadn't yet re-resolved the device's friendly name, and if pairing completed before that happened, bluetoothd failed with "Error creating port!" — the Bluetooth link paired and encrypted fine, but the /dev/cu.* tty was never created, so nothing above the ACL layer could talk to it. Fix: a short blueutil --inquiry 3 between unpair and pair, resolving the name first. Verified 5/5 clean reconnects afterward, versus roughly 1/4 without it.

A separate, earlier finding: pyserial asserts DTR by default when opening a port, and on this board DTR is wired through to EN (reset) — opening the USB serial port during an active Bluetooth session would reset the chip and kill the session. Fixed by never opening USB serial during a live Bluetooth session, and using dsrdtr=False when diagnosing over USB.

VL53L0X — "no I2C devices found" traced to unsoldered header pins

  • Symptom: a fresh VL53L0X breakout scanned as completely empty on the I2C bus, across a long list of ruled-out causes — XSHUT floating vs. tied high, VIN at 3.3V vs. 5V, SDA/SCL swapped, alternate GPIOs, a slower I2C clock, even a second brand-new sensor.
  • Cause: the header pins were never soldered — just pushed through the board's through-holes and resting against the breadboard. A multimeter continuity check passed every time, because pressing a probe onto the pin forced a contact that wasn't present in the board's resting state.
  • Confirmed by: running the I2C scan in a tight loop while physically pressing on the header pins — the sensor showed up correctly at its real address, 0x29, during sustained contact, and dropped out the instant contact broke.
  • Fix: solder the header pins. No wiring or firmware change was needed — the pin assignments and test sketch were already correct.

The takeaway that carries beyond this one sensor: a passing continuity/idle-voltage check only proves a connection is fine while a probe is actively pressed on it — it can't rule out a mechanically unreliable joint that fails under the board's own resting weight. Catching the fault live, mid-scan, while wiggling the connection was the only test that actually distinguished those two cases.

Current status

As of this build: all four wheels drive correctly in both directions and pivot turns, verified over Bluetooth on battery power with USB fully unplugged; the web D-pad drives the real motors, not just the test buttons; Bluetooth reconnects cleanly and repeatedly; and the servo + ToF sensor are each confirmed working in an isolated test sketch. Blocked on soldering the ToF sensor's header pins (no iron on hand) before that connection is reliable outside of someone physically holding it in place.

Next: solder the sensor, re-verify it under normal resting conditions, merge servo + sensor control into the main drive firmware so Apollo1 can drive and sense at the same time, and then start on the actual swarm/autonomy logic — obstacle avoidance or mapping using the distance sensor — that the "colony" part of this project is named for. Right now there is exactly one robot; the swarm is still ahead.

Repository

Firmware, control scripts, and the web UI: github.com/dhruvauppaluri/swarm-project. Flash firmware/motor_polarity_test/motor_polarity_test.ino for drive, or firmware/servo_sensor_test/servo_sensor_test.ino to test the perception arm in isolation; run control/web_ui/server.py for the browser D-pad.
