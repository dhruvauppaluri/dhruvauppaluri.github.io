Apollo Colony — Swarm Robotics Platform (In Progress)

A multi-robot swarm platform, starting with Apollo1: a differential-drive "queen" robot that reuses the chassis from the Apollo 1 rover build, now with camera-based obstacle avoidance fused with a time-of-flight sensor, a WebSocket/Bluetooth control bridge, and a SenseCAP Indicator touchscreen control panel.

github.com/dhruvauppaluri/swarm-project

Project Overview

  • Role: solo project, ongoing
  • Status: drive, distance sensing, and camera-based obstacle avoidance (fused with the ToF sensor) are all verified live on the first robot; a touchscreen control panel is flashed and verified live end-to-end; swarm/multi-robot logic is next
  • Key hardware: the chassis from the Apollo 1 rover build, rebuilt around 2-motor differential drive — ESP32-WROOM-32 DevKitC, a single L298N H-bridge, a fixed-mount VL53L0X time-of-flight sensor, a Seeed XIAO ESP32S3 Sense camera board, and a SeeedStudio SenseCAP Indicator D1 (ESP32-S3 + RP2040, 480×480 touchscreen) as a control panel
  • Stack: Arduino/C++ firmware, Python (FastAPI, WebSocket, OpenCV, YOLOv8n via ultralytics, pyserial), LVGL for the touchscreen UI, macOS blueutil for Bluetooth session management
  • Repository: github.com/dhruvauppaluri/swarm-project

Note: this builds on Apollo 1, the WeaveHacks 4 EEG rover — that project's chassis is the starting point here, but this is a separate, ongoing rebuild in its own swarm-project repo: the Arduino Uno and per-motor transistor switching are gone, replaced by an ESP32 platform with a new drive layout, a WebSocket/Bluetooth control bridge, a camera-based perception stack, and a touchscreen control panel. The robot is internally named "Apollo1" here too (the queen of the planned "Apollo Colony" swarm), which is a coincidence worth flagging so the two aren't mixed up.

Objective

The goal is a colony of small robots that can eventually coordinate as a swarm. Before any swarm logic makes sense, one robot has to actually drive, sense, avoid obstacles, and stay reachable and controllable — that's Apollo1, the queen: the existing chassis, carried over and rebuilt with a simpler, more reliable drive layout, a real perception stack, and control surfaces (web D-pad, touchscreen panel) that shake out the platform before a second robot is even started.

The project has moved from a hardware/control-plane exercise into a working reactive robot: it drives, senses distance, sees and avoids obstacles with a camera, and can be started/stopped/monitored from a touchscreen panel over WiFi. Multi-robot coordination is the next phase, not yet built.

System architecture

  • Chassis: the platform from the Apollo 1 rover build, rebuilt around a single L298N H-bridge driving 2 motors in differential drive — simpler and more reliable than the 4-motor/2-module skid-steer layout it replaced, after a persistent single-channel wiring fault on the old layout.
  • Drive: latched commands (w/a/s/d/x) over both USB serial and Bluetooth SPP, mirrored to both at once so either link can debug the other.
  • Distance sensing: a fixed-forward VL53L0X time-of-flight sensor, plus a firmware-side autonomous obstacle-avoidance state machine.
  • Camera-based obstacle avoidance: a Seeed XIAO ESP32S3 Sense streams MJPEG over its own WiFi link; a Python script runs YOLOv8n on the live feed, decides a drive command from detected-object position and size, and fuses it with the VL53L0X reading — the point sensor can only escalate caution, never override the camera toward "clear." Verified live: a held obstacle triggered an immediate stop at the frame it crossed a distance threshold, with auto-resume once it was pulled back.
  • Control bridge: a FastAPI + WebSocket server (control/web_ui/server.py) owns the single Bluetooth serial connection to the robot and fans it out to any number of clients at once — the browser D-pad, the vision script, and the touchscreen panel all share the same link without fighting over the serial port.
  • Touchscreen control panel: a SeeedStudio SenseCAP Indicator D1 (ESP32-S3 + RP2040 co-processor, 480×480 touchscreen) runs an LVGL UI with a tabbed layout — a live "Apollo 1" start/stop + status tab, and a reserved "Drone 1" placeholder tab for the next robot. Since the Indicator's ESP32-S3 only has BLE radio hardware (no Classic Bluetooth), it reaches the robot over WiFi as a WebSocket client of the same bridge server the browser D-pad uses.

Implementation

Chassis redesign: from 4-motor skid-steer to 2-motor differential drive

The platform started as the 4WD chassis carried over from the Apollo 1 rover build, driven by 2 L298N modules in skid-steer. After isolating a persistent single-channel wiring fault to one motor's connector (confirmed by a swap test — a known-good motor failed on that channel too, and the suspect motor worked fine elsewhere) rather than the motor or driver itself, the front two wheels were dropped for a free-swiveling caster and the drive rebuilt around a single L298N and 2 rear motors. Simpler electronics, one fewer failure surface, and — since the design no longer needed a servo panning the distance sensor for wider coverage — the servo was retired for good once the camera gave the robot passive wide-field awareness in a single frame with no moving parts.

Camera-based obstacle avoidance

control/vision/object_avoidance.py runs YOLOv8n on the XIAO ESP32S3 Sense's live MJPEG stream, turns bounding-box position (left/center/right) and size (a proxy for closeness) into a drive command, and cross-checks it against the VL53L0X reading polled over the existing serial link. A point-blank ToF reading overrides the vision decision outright and stops immediately, bypassing the usual multi-frame debounce; a moderately-close reading while vision reports clear triggers a turn, catching obstacles the camera missed. Both override paths have been confirmed live against a real obstacle, including full auto-resume once it was removed.

SenseCAP Indicator touchscreen panel

The touchscreen sketch (firmware/sensecap_display_control) renders an LVGL tab view with START/STOP buttons and a live status label that mirrors whatever the robot's own firmware last printed over serial — forwarded through the WebSocket bridge as plain text. Before flashing this project's own firmware, the board was found still running an unrelated hackathon demo (an environmental air-quality logger on its RP2040 co-processor, and a WiFi-connected ESP-IDF app on its ESP32-S3) — confirmed by reading both processors' live serial output and, read-only, the ESP32-S3's flash image, rather than assuming the board was blank. Flashing this project's own sketch required dropping the upload baud rate (the default 921600 was unreliable on this board's USB path, corrupting mid-transfer; 115200 flashed clean and hash-verified) — and getting from a rendered-but-unreachable screen to a fully live status feed required a real fix in the bridge server itself (below).

Display/touch hardware bring-up (ST7701 panel init, PCA9555 IO-expander wiring, the software-SPI command bus, and the LVGL↔Arduino_GFX glue) is adapted near-verbatim from LongDirtyAnimAlf/SenseCap — the reference implementation Seeed's own official wiki links to for this board. The touchscreen driver is mmMicky/TouchLib, also linked from Seeed's docs. Only the WiFi/WebSocket bridge client, the start/stop/status UI, and the tabbed multi-vehicle layout are original to this project.

Web control UI & bridge

control/web_ui/server.py holds the one shared Bluetooth serial connection and fans status/RX lines out to every connected WebSocket client — browser D-pad, vision script, and touchscreen panel alike — so none of them fight over the serial port. The browser page (control/web_ui/index.html) is a plain D-pad with keyboard shortcuts and a live log of sent commands and device responses.

Debugging & iteration

SenseCAP display: WebSocket bridge dropped the connection immediately after handshake

Once the touchscreen panel was flashed and confirmed rendering by direct visual inspection (Serial output turned out not to route to the board's USB-serial path at runtime, so serial logging was a dead end for this one — the screen itself was the only reliable signal), it connected to the bridge and immediately disconnected again, in a tight loop, 3 times in under 10 seconds. The server-side traceback pointed at an unhandled exception: the bridge's initial status message was sent to a freshly-accepted client before the code's own try/except block, so when the ESP32's WebSocket client closed the raw connection right after the handshake — before it was ready to receive, a known rough edge on constrained WebSocket clients — the exception went uncaught and the dead client was never cleaned up. Moving that first send inside the try block and adding a short settle delay fixed it: the connection held stable for 25+ seconds afterward, versus repeated drops before. Confirmed working end-to-end when the display's status label started tracking the bridge's real live broadcasts instead of a static fallback string.

Bluetooth SPP — reconnects, three stacked bugs, then a fourth "silent stale" mode

Getting Bluetooth SPP to reconnect cleanly took three independent, stacked fixes, each found by reading raw system logs instead of guessing from symptoms: macOS caching a stale RFCOMM channel number after a reboot (fixed with a scripted unpair → pair → connect cycle before every session), the ESP32's own Bluetooth bond store disagreeing with a freshly re-paired host link key (fixed by clearing the firmware's bond on every disconnect, not just at boot), and a macOS name-resolution race that silently failed to create the /dev/cu.* tty even though pairing succeeded (fixed with a short discovery inquiry between unpair and pair). A fourth, different failure mode later showed up under live use: the link reports connected and accepts writes, but nothing ever comes back — not a repeat of the earlier bugs, since those all fail visibly at a specific layer. Current workaround is restarting the bridge server to force a full reconnect cycle; a permanent auto-recovery fix (treating "no response within N seconds" as a forced-reconnect trigger) isn't implemented yet.

VL53L0X — "no I2C devices found" traced to unsoldered header pins

  • Symptom: a fresh VL53L0X breakout scanned as completely empty on the I2C bus, across a long list of ruled-out causes — XSHUT floating vs. tied high, VIN at 3.3V vs. 5V, SDA/SCL swapped, alternate GPIOs, a slower I2C clock, even a second brand-new sensor.
  • Cause: the header pins were never soldered — just pushed through the board's through-holes and resting against the breadboard. A multimeter continuity check passed every time, because pressing a probe onto the pin forced a contact that wasn't present in the board's resting state.
  • Confirmed by: running the I2C scan in a tight loop while physically pressing on the header pins — the sensor showed up correctly at its real address, 0x29, during sustained contact, and dropped out the instant contact broke.
  • Fix: solder the header pins. No wiring or firmware change was needed — the pin assignments and test sketch were already correct.

The takeaway that carries beyond this one sensor: a passing continuity/idle-voltage check only proves a connection is fine while a probe is actively pressed on it — it can't rule out a mechanically unreliable joint that fails under the board's own resting weight. That same "looks fine at every layer you can directly observe, but isn't" shape showed up again later in the WebSocket bridge bug above, at a completely different layer of the stack.

Current status

As of this build: the rebuilt 2-motor chassis drives correctly in both directions and pivot turns over Bluetooth; the VL53L0X and camera-based obstacle avoidance are fused and verified live, including confirmed override stops against a real obstacle; the SenseCAP Indicator touchscreen panel is flashed, renders its UI, and holds a live WebSocket connection to the bridge with a real-time status feed. The Bluetooth link between the bridge and the robot itself can still go silently stale under live use (workaround: restart the bridge server) — a permanent fix isn't in yet.

Next: harden the Bluetooth link with a real auto-recovery fix instead of a manual restart, and start on the actual swarm/autonomy logic — multiple robots and coordination — that the "colony" part of this project is named for. Right now there is exactly one robot; the swarm is still ahead.
