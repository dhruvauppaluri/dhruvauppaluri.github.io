Malleable FPGA AI Platform

A hardware/software research platform asking whether an FPGA accelerator can adapt its organization to the neural network it runs, instead of forcing every model through one permanently fixed datapath.

View source View ASIC project

Overview

  • Role: solo research and RTL implementation; software toolchain scoped for an independent ML contributor.
  • Current RTL: parameterized signed INT8 MAC and dot-product lanes, multi-tile accumulation, bias, integer requantization, INT8 saturation, optional ReLU, and malleable_accelerator_top for up to four dense layers with ping-pong activation buffers.
  • Verification: self-checking SystemVerilog benches; seeded randomized tests through the MAC, dot product, post-processing, tiled reductions, single layers, and complete 7→5→3 networks; make verify runs simulation, Verilator lint, and coarse Yosys synthesis in GitHub Actions.
  • Software: golden model, quantization pipeline, model descriptor formats, and configuration analyzer are documented but not implemented yet (see the repository’s ML contributor roadmap).
  • Next hardware: extend Cyclone V Quartus projects to the integrated top, then add a board-specific host interface and measured resource/timing results.
  • Longer term: precompiled hardware personalities, optional partial reconfiguration on Kria/Zynq UltraScale+, and eventually a standalone decoder-only language model on FPGA-only inference.

The research question

Neural networks differ in compute shape, memory footprint, and bandwidth pressure. A fixed accelerator picks one compromise before it sees the workload. This project explores inspecting the model first, estimating resource and traffic needs, then selecting or generating an accelerator layout that fits better—starting with parameterized RTL personalities on Cyclone V and, later, swapping precompiled accelerator regions while a stable shell keeps host I/O and memory running.

The FPGA performs inference. Training, quantization, hardware selection, and bitstream compilation stay on a host. The device selects from hardware that was generated and compiled ahead of time; it does not synthesize new RTL at runtime.

Three-stage research program

Stage 1 is the original standalone FPGA accelerator and must produce complete FPGA-only results without a GPU. Stages 2 and 3 are later extensions: an independent GPU baseline, then a hybrid that uses the FPGA for candidate-token generation and the GPU for verification—only if measured end-to-end results beat communication and verification overhead. 

Stage 1 ──► standalone malleable FPGA (this repository)
    │
    ├──► Stage 2: independent GPU baseline
    │
    └──► Stage 3: FPGA + GPU hybrid (after both stand alone work)

GPU and hybrid work are explicitly out of scope until Stage 1 meets its completion criteria: independent reference agreement, end-to-end inference or token generation, latency and throughput, FPGA utilization, and documented numeric effects.

System architecture

trained model ──► INT8 quantization ──► model descriptor
                              │                    │
                              ▼                    ▼
                         weights / vectors    hardware analyzer ◄── FPGA limits
                              │                    │
                              ▼                    ▼
                         host runtime ──► selected personality / bitstream
                              │
                              ▼
                    FPGA: buffers ──► MAC lanes ──► dot products ──► INT32 acc
                              │              bias ──► requant ──► ReLU ──► out
                              └── benchmarks and results feed back to analyzer

The analyzer (planned in software) connects model shape to lane count, buffer sizes, tile geometry, and dataflow. Today the verified compute path and a board-independent 32-bit configuration port exist in RTL; the host-side export, analyzer, and deployment loop are the next software milestones.

What works today (RTL)

Development follows the numeric contract in the repository: signed INT8 multiply, signed INT32 accumulate, explicit overflow reporting, and separate post-processing stages so scaling and activations are not hidden inside the MAC. 

acc_next = acc + (signed_int8_activation × signed_int8_weight)

tiles ──► parallel INT8 MAC lanes ──► reduction ──► INT32 accumulator
                              │
                              ▼
              bias + integer requant + INT8 sat + optional ReLU

malleable_accelerator_top is the autonomous dense-network MVP. Its default personality supports four dense layers (up to 64×64), four parallel INT8 lanes, internal weight and parameter memories, and alternating activation banks so one layer’s output becomes the next layer’s input without a host copy. A single start pulse runs the full network; status exposes busy, done, overflow_error, and config_error.

Randomized regression coverage includes 10,000 MAC cases, 2,500 dot-product cases, 10,000 post-processing cases, 1,000 tiled reductions, 1,000 dense layers, and 100 complete 7→5→3 networks—all seeded for reproducibility.

Memory and tiling

Large layers are broken into tiles so weights and activations move through limited on-chip memory. Ping-pong activation buffers are in place between layers; double buffering to overlap external transfer with compute is still on the roadmap. Small working sets target FPGA block RAM; larger tensors are expected to stream through explicit load/compute/store stages once a board shell exists.

Stage 1 roadmap (selected milestones)

  1. Verified arithmetic and post-processing — complete: MAC, dot product, tiled accumulation, bias, requantization, ReLU, and dense-network top in simulation.
  2. Software golden model and artifacts — next: bit-accurate Python reference, quantization spec, versioned descriptors, and exported vectors for RTL cross-check (ML contributor roadmap).
  3. Measured FPGA implementation: Quartus compile of malleable_accelerator_top, resource and timing on Cyclone V, host transport and benchmark harness.
  4. Malleability loop: multiple precompiled personalities; benchmark lane, buffer, tile, and dataflow choices; analyzer-driven selection.
  5. Advanced platform: Kria or Zynq UltraScale+ shell with partial reconfiguration; extend toward a small decoder-only LM with FPGA-only token generation.

Current limits

Evidence today is RTL simulation, Verilator lint, coarse Yosys synthesis, and CI—not yet board throughput, power, or a live partially reconfigurable deployment. Quartus projects exist for the MAC and dot-product blocks with 100 MHz constraints; they still need extension to the integrated top and a machine with Quartus Prime Lite for real fit/timing numbers. Without the golden model, RTL and software have not yet been cross-checked against a shared exported artifact beyond the self-checking benches.

Relationship to the ASIC project

This is separate from the Jane Street protocol-emulator ASIC. The ASIC is a compact, deterministic protocol processor with fixed fabricated logic. MalleableAI-FPGA reuses the same engineering habits—small modules, paired testbenches, reproducible builds—but does not share RTL or combine the two architectures.
