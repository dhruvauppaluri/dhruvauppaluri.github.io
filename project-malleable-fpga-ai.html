Malleable FPGA AI Platform

A hardware/software research project asking whether an FPGA accelerator can adapt to the neural network it is running, instead of forcing every model through one permanently fixed datapath.

View source View ASIC project

Project Overview

  • Role: solo research and implementation project
  • Current hardware: a signed INT8 multiply-accumulate unit and a four-lane parallel dot-product engine with INT32 accumulation
  • Current software: a bit-accurate Python reference, JSON model descriptor, and resource-aware model analyzer
  • Verification: 10,000 randomized MAC cases and 2,500 randomized dot-product cases match the Python model
  • Target: begin on a Cyclone V FPGA, then grow from parameterized RTL toward model-selected hardware personalities and partial reconfiguration

The Research Question

Neural networks vary widely. One model may be limited by matrix multiplication, another by on-chip memory, and another by the cost of moving tensors to external memory. A fixed accelerator chooses one compromise before it sees the workload. This project explores a different path: inspect the model first, estimate its compute and memory shape, then choose or generate an accelerator organization that fits it better.

“Malleable” has several levels. The near-term version is parameterized RTL compiled for different lane counts and buffer sizes. A later version can select between complete prebuilt FPGA images. The long-term research goal is a fixed control shell with a partially reconfigurable accelerator region that changes without rebuilding or replacing the whole system.

What Works Today

The project starts at the arithmetic contract, not at a large demo. The MAC accepts signed 8-bit activations and weights, produces a signed 16-bit product, and accumulates into a signed 32-bit value. It also reports signed overflow explicitly. Four MAC lanes form the first parallel dot-product unit. 

acc_next = acc + (signed_int8_activation × signed_int8_weight)

4 lanes/cycle ──► lane products ──► signed reduction ──► INT32 accumulator

Self-checking SystemVerilog tests and a bit-accurate Python model share the same numerical rules, including wrapping and overflow behavior. GitHub Actions runs the RTL simulations, Python tests, and model-analyzer checks on every change.

Hardware/Software Co-Design

model descriptor ──► Python analyzer ──► resource / traffic estimate
                                               │
                                               ▼
host + external memory ──► tiled buffers ──► MAC lanes
                                               │
                                               ▼
                              INT32 accumulation, bias,
                              requantization, ReLU ──► INT8 output

The model descriptor records layer sizes, tensor shapes, and numeric format. The analyzer estimates operations, parameter storage, activation storage, and the pressure each layer places on compute lanes and memory. That software layer is important because changing hardware only helps when the system can explain which configuration a model needs and why.

The first complete inference target is a tiny dense network. Its layers will be broken into tiles, accumulated across multiple cycles, then passed through bias addition, requantization, and ReLU. That end-to-end path is the next milestone; it is not presented as complete yet.

Memory Strategy

More DRAM does not automatically make inference faster. The important question is how much data can stay close to the MAC lanes and how efficiently the design reuses it. Small working tiles belong in FPGA block RAM; larger weights and activations can live in the board's external memory and move through explicit load/compute/store stages.

Desktop DDR4 DIMMs would remain host memory rather than connecting directly to a typical Cyclone V board. The host can preprocess models and stream tensors, while the board uses its own supported memory interface. This keeps the early architecture realistic and makes bandwidth a measured design constraint instead of an assumption.

Path to a Malleable Accelerator

  1. Verified arithmetic foundation — complete: signed INT8 MAC, overflow behavior, four-lane dot product, and Python equivalence.
  2. Complete one network — next: tiled dense layers, persistent accumulation, bias, requantization, ReLU, and end-to-end comparison.
  3. Scale the datapath: parameterize lane count, tile shape, buffers, and memory movement; measure throughput and resource use.
  4. Close the model-to-hardware loop: use analyzer output and benchmark feedback to select a hardware personality.
  5. Explore partial reconfiguration: keep a stable shell for host I/O and memory while swapping only the accelerator region from prebuilt partial bitstreams.

Partial reconfiguration would not require a permanent Quartus connection at runtime. Quartus is used ahead of time to build and validate the full and partial bitstreams; deployed control software loads one of those approved images when the workload changes.

Current Limits

The repository includes Cyclone V Quartus project files and a 100 MHz timing constraint, but the design has not yet been fitted and timed in Quartus on the target board. The current evidence is simulation, randomized software equivalence, CI, and portable RTL—not measured FPGA throughput or a demonstrated partially reconfigurable system. Those boundaries are part of the project plan, not hidden behind the long-term pitch.

Relationship to the ASIC Project

This is separate from the Jane Street protocol-emulator ASIC. The ASIC is a compact, deterministic protocol processor with fixed fabricated logic. This FPGA project is the larger research track: it can spend more area on neural-network arithmetic, use external memory, measure multiple architectures, and eventually change part of its hardware configuration around a model.
